memory for agentic sessions · the main page · recall

The knowledge store holds what is true beyond one project, and how a recurring task is done, filed by topic rather than by repository. The same unattended pipeline feeds it: encode homes a trace by its type, consolidate folds a topic's traces into its pages, recall ranks the pages beside the memories.

Built: the store, encode's and consolidate's split, remember --topic, recall, show and chart over it. Not built: rehoming the existing memories, graduation into and out of the store (next).

The problem

Every memory is filed under the repository a session worked in. That suits a preference or a project's decision; it misfiles what the work discovered about a tool (how launchd stops a job, what a llama.cpp flag really does) and the steps of a task done again and again. Such a fact lands in whichever bank the session happened to touch, one short note per fact, and a session in another repository never earns it the bank's bonus. The owner, 2026-11-14: "memories are good for my preferences and project recall, but i'm finding we should have a place for general knowledge and playbook type structures".

Three long-term systems

Memory science names three; sandman stored one. On disk and in the CLI the words are the owner's: knowledge and playbook.

A reviewed memory about one repository's decision stays a memory even when the tool is general: "grove sets ExitTimeOut 2" is grove's project memory; "launchd kills a job past its ExitTimeOut" is knowledge under launchd.

The store

<topic> is a slug: lowercase letters, digits and -, a letter or digit first (launchd, llama-cpp, grove-release).

<root>/

  knowledge/launchd/playbook_swap_a_launchd_daemon.md    a playbook
  traces/@launchd/playbook_drain_a_daemon.md             a trace awaiting consolidate
  traces/-work-grove/project_exit_timeout_2.md           a memory trace, by repository
  .pruned/2026/11/14/093000-@launchd-ops.json            consolidate's reply, as for a bank
  • pages — the memory file format: flat frontmatter, type knowledge or playbook, topic, created, updated once merged, source the consolidate stamp; the session and archive of the trace that started it, and sessions every session it descends from, merges included. The cycle adds id, from and origin (the note, not built): a page born of a rung-1 graduation names its memories on from: and starts with no sessions.
  • traces — a topic's wait in traces/@<topic>/. A bank key is letters, digits and -, so @ never collides with one, and the notes reader, which skips only . and _, finds them. Inside the pipeline a topic's bank is @<topic> throughout: the ledger's consolidate lines, .pruned/ names, reflect's evidence.
  • paths — show knowledge/<topic>/<file>.md reads a page, show traces/@<topic>/<file>.md a trace; chart lists pages as knowledge, memories' shape with topic for bank.

How a page is written and revised

One episode, two homes; one consolidate job, two targets.

  • encode — the contract gains the two types and topic, required for them, in place of about; a knowledge type without a slug topic fails the episode. The guidance says when a fact is knowledge (it holds for any project on the same tool), when a sequence is a playbook (a task done more than once, or steps worth repeating), and that a later episode showing a step wrong writes a corrected playbook trace under the same topic.
  • consolidate — picks a quiet @<topic> as it picks a bank and sends the topic's pages as the bank's memories. merge is the common case: the trace folds into the page, the page comes back whole and replaces the old, updated set, the old under .pruned/. keep starts a page, and in a topic takes knowledge or playbook only; prune drops a trace.
  • by hand — sandman remember "<body>" --type playbook --topic launchd writes the trace at once; --topic alone means knowledge, and a type without a slug topic is refused, exit 2. The MCP remember tool takes type and topic.
  • reflect — no code of its own: it reviews the guidance that carries these rules, and its evidence reads a topic's ops and remembers as a bank's. A page merged often is growing as it should; its guidance says so.

The playbook's shape

Fixed, so a reader finds the step and the hazard without reading the history.

  • When: the situation it is for.
  • Steps: numbered, one action each, its command when there is one.
  • Watch for: what went wrong before and how it showed, dated. A trace that proves a step wrong replaces the step and adds the failure here; the old step does not survive beside the new.

Steps:
1. Install the binary in place.
2. `launchctl kickstart -k gui/$(id -u)/<label>`.
3. `<daemon> status`: the version matches the build.

kickstart -k is one atomic restart.

How recall treats it

Pages and their traces are ordinary candidates in the same pass: the gate, BM25, the embeddings, the decision model and the cap of 6. Their label is knowledge · <topic>, which is the head embedded and the decision model's Memory (knowledge · launchd): …; it matches no repository, so no bank bonus, and the line shows the type: 1.00 Swap a launchd daemon (playbook · knowledge/launchd/playbook_swap_a_launchd_daemon.md), a trace marked ~. Knowledge is never in the always-set, even pinned. The tick's embed job covers the pages as it covers memories. With no knowledge on disk, every pinned recall output is unchanged.

Next

Not built.

  • rehoming — a one-time, reviewed pass over the 645 memories, starting with the 109 reference ones (measured 2026-11-13, recall): a model proposes per memory keep (stays episodic), knowledge or playbook with a topic, written as a plan file; the owner reviews it; the apply step writes each moved one as a trace under traces/@<topic>/ (its created, session and quotes kept) and moves the original to .pruned/, so consolidate builds the pages and every step is recoverable.
  • promotion — memories graduate into pages automatically (rung 1); a page or playbook used across sessions is proposed as a skill or a guidance line (rung 2), a lesson relearned as a mechanism (rung 3), the owner approving both (graduation).
